# 设备指纹收集分析

> 基于 Claude Code 反编译源码分析

## 概述

Claude Code 实现了一套多维度的设备指纹系统，覆盖从硬件层（CPU 架构）到应用层（版本号、终端类型）再到行为层（消息指纹、文件操作模式）的多个维度。指纹数据通过独立的分析管道发送，不与 LLM API 请求混合。

## 一、设备唯一 ID

**文件**: `src/utils/config.ts`（约第 1757-1766 行）

### 生成机制

```typescript
export function getOrCreateUserID(): string {
  const config = getGlobalConfig()
  if (config.userID) {
    return config.userID
  }
  const userID = randomBytes(32).toString('hex')
  saveGlobalConfig(current => ({ ...current, userID }))
  return userID
}
```

### 特征

| 属性 | 值 |
|------|-----|
| 格式 | 64 字符十六进制字符串（32 随机字节） |
| 生成时机 | 首次运行时创建 |
| 持久化位置 | `~/.claude/config.json` |
| 生命周期 | 永久存在，除非用户手动删除配置文件 |
| 使用频率 | 每个分析事件都携带 |
| 字段名 | `deviceId` 或 `device_id`（取决于 camelCase/snake_case 上下文） |

## 二、可信设备令牌（Bridge 会话）

**文件**: `src/bridge/trustedDevice.ts`

### 注册信息

```typescript
{ display_name: `Claude Code on ${hostname()} · ${process.platform}` }
// 示例: "Claude Code on MacBook-Pro · darwin"
```

### 特征

| 属性 | 值 |
|------|-----|
| 令牌类型 | 服务端分配的设备令牌 |
| 过期策略 | 90 天滚动过期 |
| 存储位置 | 系统钥匙链（Keychain） |
| 注册端点 | `POST /api/auth/trusted_devices` |
| 注册时机 | 登录时自动注册（受 feature flag `tengu_sessions_elevated_auth_enforcement` 控制） |
| 携带数据 | 机器 hostname + 操作系统平台 |

### 安全影响

- hostname 可能泄露用户名或机器名（如 `chen-MacBook-Pro.local`）
- 令牌存储在系统钥匙链中，相对安全

- **memoize 缓存**: `buildEnvContext` 使用 memoize 包装，整个会话期间只计算一次

- **运行时检测**: 通过 `which` 命令检测 python、ruby、go、rust 等是否安装
- **Linux 发行版检测**: 读取 `/etc/os-release` 文件

## 六、仓库指纹

**文件**: `src/services/analytics/metadata.ts`（约第 739 行）

### 实现

```typescript
// 对仓库远程 URL 做 SHA256 哈希，取前 16 字符
rh: repoRemoteHash  // 例如: "a3f2b1c4d5e6f7g8"
```

### 特征

- 原始 URL 不发送，只发送哈希前缀
- 用于服务端关联仓库维度的数据
- 通过 `git remote get-url origin` 获取远程 URL

## 七、消息指纹

**文件**: `src/utils/fingerprint.ts`

### 算法

```
fingerprint = SHA256(SALT + msg[4] + msg[7] + msg[20] + version)[:3]
```

### 参数

| 参数 | 值 |
|------|-----|
| SALT | `59cf53e54c78`（硬编码，与后端校验一致） |
| 提取字符位置 | 第 4、7、20 个字符 |
| 版本号 | `MACRO.VERSION`（编译时注入） |
| 输出长度 | 3 个十六进制字符 |
| 用途 | Claude Code 来源归属追踪 |

### 使用场景

- 嵌入到 `x-anthropic-billing-header` 中：`cc_version=1.0.50.a3f`
- 版本号后的 `.a3f` 就是消息指纹

## 九、数据发送目标汇总

### 发送通道

| 通道 | 端点 | 协议 | 频率 |
|------|------|------|------|
| 一方日志 (1P) | `api.anthropic.com/api/event_logging/batch` | OpenTelemetry + Protobuf | 每 10 秒批量，最多 200 条 |
| Datadog | `http-intake.logs.us5.datadoghq.com/api/v2/logs` | HTTP JSON | 64 种预定义事件 |
| GrowthBook | A/B 实验平台 | HTTP | 实验分配时 |

### 各通道收到的数据

| 数据类型 | 1P | Datadog | GrowthBook |
|----------|-----|---------|------------|
| 设备 ID | Yes | Yes | Yes |
| 会话 ID | Yes | Yes | Yes |
| 环境指纹（完整） | Yes | Yes（剥离 PROTO 字段） | 部分 |
| 进程指标 | Yes | No | No |
| 用户数据 | Yes | No | 部分 |
| 仓库哈希 | Yes | No | No |
| 消息指纹 | Yes（通过归属头） | No | No |
| 订阅类型 | Yes | No | Yes |
| API 代理主机名 | No | No | Yes |

## 十、网络层数据

### 主动收集的网络信息

| 数据 | 是否主动收集 | 说明 |
|------|-------------|------|
| IP 地址 | 否 | 服务端通过 HTTP 请求天然获取 |
| MAC 地址 | 否 | — |
| DNS / 网关 / 子网 | 否 | — |
| WiFi SSID | 否 | — |
| 代理主机名 | 是 | 仅当用户配置了非官方 `ANTHROPIC_BASE_URL` 时 |
| 机器 hostname | 是 | 可信设备注册时发送 |
| 远程环境标识 | 是 | 容器 ID、远程会话 ID 等 |

### 结论

网络层指纹采集很克制，没有像浏览器指纹那样采集网卡、IP、DNS 等信息。但服务端通过 HTTP 请求天然获得客户端 IP。

## 十一、数据流向图

```
用户操作
  │
  ├──→ LLM API 调用 (/v1/messages)
  │      ├─ HTTP Headers: session_id, user_agent, x-app
  │      ├─ metadata.user_id: device_id, account_uuid, session_id
  │      ├─ system prompt: 工作目录、OS、Shell、git 状态
  │      └─ 不含完整设备指纹
  │
  └──→ 分析事件管道 (logEvent)
         ├─ core_metadata: 完整环境指纹 + 进程指标
         ├─ user_metadata: 用户追踪数据
         ├─ event_metadata: 事件特定数据
         ├─→ 1P (api.anthropic.com/api/event_logging/batch)
         ├─→ Datadog (http-intake.logs.us5.datadoghq.com)
         └─→ GrowthBook (A/B 实验)
```
